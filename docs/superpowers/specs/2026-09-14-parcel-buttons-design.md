# Parcel buttons, carrier stickers and service-bot patterns — design

Date: 2026-09-14 · Branch: `main` · Status: built and deployed 2026-09-14 (`139ec16`, `415a2d0`, `5006794`, `c44bfcc`, `c211676`); keyboards live in `vn_parcel_bot/keyboards.py`

## 1. Why

The user wants the bot to feel like popular Telegram service bots (their example: a downloader bot with action and URL buttons under each result), with a rename option, carrier-logo stickers from Telegram packs, and patterns agy researched (report kept in the session scratchpad; claims checked against the Bot API where they matter). The green/red emoji progress bar was built separately (`897bcf3`).

## 2. Decisions (from the chat)

| Topic | Decision |
|---|---|
| Buttons | ✏️ Đổi tên, 📜 Hành trình, 🔄 Kiểm tra, 🗑 Xóa, 🔗 Tra cứu ↗ (URL) |
| Where | Full card buttons under update messages and add confirmations; `/list` and digests get numbered picker buttons |
| On tap | Edit the same message in place; rename uses a short prompt that is deleted afterwards |
| Stickers | From packs the user provides; admin maps one sticker per carrier; sent before that carrier's update messages |
| agy extras | Sound only on big moments; flood-control retry; `/list` pagination; share link per parcel |

Out of scope: custom emoji entities (bots need a purchased Fragment username), message effects, Mini Apps, group chats, storing sticker files locally, animations generated by the bot.

## 3. Buttons

### 3.1 Callback data

`p:<parcel_id>:<action>[:<page>]` for parcel actions (the optional page remembers the list a card was opened from) and `l:<page>` for list pages, always under Telegram's 64-byte limit and never containing a tracking code. Actions: `card` (show card), `his` (history), `chk` (check now), `ren` (rename), `del` (ask to remove), `dok` (confirm remove), `dno` (cancel remove), `shr` (share link). Handlers are stateless: every tap reloads the parcel from the database, so buttons keep working after restarts.

### 3.2 Keyboards (`bot/keyboards.py`)

- `card_keyboard(parcel, link_url)`: `[✏️ Đổi tên] [📜 Hành trình]`, `[🔄 Kiểm tra] [🗑 Xóa]`, `[📤 Chia sẻ] [🔗 Tra cứu <carrier> ↗]`. The URL is the carrier module's link, else the 17TRACK link; unresolved parcels link to 17TRACK.
- `history_keyboard(parcel_id)` / `share_keyboard(parcel_id)`: `[⬅ Quay lại]`.
- `confirm_remove_keyboard(parcel_id)`: `[✅ Xóa] [↩ Hủy]`.
- `list_keyboard(parcels_on_page, page, pages)`: numbered buttons (global list numbers, up to 5 per row) and, when `pages > 1`, `[⬅️] [page/pages] [➡️]` (the middle button is inert: `l:<page>`).
- A card opened from a list (`p:<id>:card:<page>`) gets one extra last row `[⬅ Danh sách]` (`l:<page>`); a card anywhere else has no back row.

### 3.3 Tap behaviour (`bot/handlers_callback.py`)

Every callback first calls `answer_callback_query` (with a short toast where useful). The parcel must exist and belong to `query.from_user.id`; otherwise the toast says `CARD_NOT_FOUND` and nothing else happens.

- `card`: edit the message to `format_parcel_card(parcel, tz)` (title, carrier, % and bar, latest status and time) with `card_keyboard`.
- `his`: edit to `format_history(parcel, events, tz)` with `history_keyboard`.
- `chk`: per-parcel cooldown `CHECK_COOLDOWN` (5 min, kept in `bot_data`); `Poller.check_parcel(parcel_id)` runs the normal fetch/store/notify path for that parcel only; then edit the card. On cooldown: toast `CHECK_TOO_SOON`.
- `ren`: send `LABEL_ASK` and set `PENDING_LABEL` (as `/label` does) with `card_message_id`; after the answer the label is set, the card message is re-rendered, and the prompt and answer are deleted.
- `del`: edit text to `REMOVE_CONFIRM` with `confirm_remove_keyboard`; `dok` removes and edits to `REMOVED` without buttons; `dno` restores the card.
- `shr`: create or reuse a share token and edit to `SHARE_LINK` (`https://t.me/<bot_username>?start=s_<token>`) with `share_keyboard`.
- Edits that fail with "message is not modified" are ignored; other `TelegramError`s are logged (type only) and the toast says `ERROR_GENERIC`.

### 3.4 Where buttons are attached

- Add confirmations (`added` and `duplicate` outcomes with a parcel) in text, `/track` and photo flows: `card_keyboard`.
- Update messages from the poller: `card_keyboard`. `Notifier.send` gains `reply_markup`.
- `/list`: first page (5 parcels) with `list_keyboard`; `l:<page>` edits to that page.
- Digests: `list_keyboard` over all parcels in the digest (numbers only, no pagination; digests stay one message).

## 4. Carrier stickers

- Admin replies to a sticker with `/sticker <carrier>` → meta `sticker:<carrier>` = the sticker's `file_id`; `/sticker <carrier> off` deletes it; `/sticker` lists which carriers have one. Unknown carrier codes are refused with the list of loaded modules.
- Before sending an update message for a parcel whose carrier has a sticker, the poller sends the sticker silently. A failing sticker (`BadRequest`, e.g. the pack owner deleted it) is logged once per carrier per process and skipped; the update message is still sent.
- No sticker is sent with add confirmations, digests or button edits.
- `Repository.delete_meta(key)` is added (used by `/sticker … off` and removed share tokens).

## 5. agy extras

- **Sound only on big moments:** update messages are silent unless the parcel just became delivered or returned, or its progress reached 95 (out for delivery). Quiet hours still make everything silent. Digests keep their sound.
- **Flood-control retry:** `TelegramNotifier.send` (and the sticker send) catch `RetryAfter`, sleep `min(retry_after, 60)` seconds and retry once; a second failure is logged and dropped as today.
- **Pagination:** covered in §3.2/§3.3 (`LIST_PAGE_SIZE = 5`).
- **Share link:** meta `share:<token>` = parcel id, `share-of:<parcel_id>` = token (reused). Token: `secrets.token_urlsafe(9)` (12 chars). `/start s_<token>` for an allowed user shows `SHARE_OPEN` (title and carrier, code blurred) with `[✅ Theo dõi] [↩ Bỏ qua]` (`s:<token>:ok` / `s:<token>:no`); ✅ adds the same tracking number (and label) to that user's own list through `ParcelService.add` and shows the normal add result with card buttons. The sharer's list is never exposed; unknown or removed tokens reply `SHARE_NOT_FOUND`.

## 6. Texts (new)

`BTN_RENAME`, `BTN_HISTORY`, `BTN_CHECK`, `BTN_REMOVE`, `BTN_SHARE`, `BTN_LINK` (`🔗 Tra cứu {carrier} ↗`), `BTN_BACK`, `BTN_BACK_LIST`, `BTN_CONFIRM_REMOVE`, `BTN_CANCEL`, `BTN_TRACK_SHARED`, `BTN_SKIP`, `CARD_NOT_FOUND`, `SHARE_LINK`, `SHARE_OPEN`, `SHARE_NOT_FOUND`, `LIST_PAGE` (`Trang {page}/{pages}`), `STICKER_SET`, `STICKER_REMOVED`, `STICKER_LIST`, `STICKER_USAGE`. Button labels stay under 20 characters.

## 7. Testing

- Keyboards: button texts, callback data format and length (< 64 bytes), URL choice, pagination rows.
- Callback handler (fake query/bot): each action, ownership refusal, cooldown, not-modified edits ignored, remove confirm/cancel, rename flow end to end with deletions, share token reuse.
- Poller: `check_parcel`, sticker sent before the update (and skipped after a failure), silent vs sound rules, update message carries the keyboard.
- Notifier: `RetryAfter` retried once.
- `/list` pagination and digest picker; `/start s_<token>` share flow; `/sticker` admin command.
- Gates as usual; no real codes, tokens or sticker ids in tests.
